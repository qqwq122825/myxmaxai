# 带宽、流量和延迟预算

以下数值是本方案的工程起点与验收目标，不是 Pro 2.7、DFM 或抖音直播伴侣的实测保证。按单路 H.264、30 FPS 计算；实际需要随动作、噪点、画面细节、编码器和模型测试调整。

## 1. 三段网络要分别算

```text
① 家里 → GPU：原摄像头视频，消耗家里的上传和服务器的下载
② GPU → 家里：处理后视频，消耗服务器的上传和家里的下载
③ 家里 → 抖音：直播伴侣最终推流，再次消耗家里的上传
```

本地上传容量不能只看第①段。若同时还有其他人上传文件、云盘同步、视频通话，需要在下列预算外预留空间。

| 档位 | ① 原视频上传目标 | ② 结果回传目标 | ③ 平台推流假设值，仅用于算预算 | 本地上传建议 | 本地下载建议 |
|---|---:|---:|---:|---:|---:|
| 720p / 30 FPS | 3–5 Mbps | 4–6 Mbps | 4–6 Mbps | ≥20 Mbps | ≥15 Mbps |
| 1080p / 30 FPS | 6–10 Mbps | 8–12 Mbps | 6–10 Mbps | ≥30 Mbps | ≥25 Mbps |

第③段最终以直播伴侣实际设置和监测值为准，上表不是抖音平台推荐或限制。

规划公式：

```text
本地上传容量 ≥ (原视频上传码率 + 直播推流码率 + 其他上传) × 1.3
本地下载容量 ≥ (回传码率 + 其他下载) × 1.3
远程入站容量 ≥ 原视频上传码率 × 1.3
远程出站容量 ≥ 回传码率 × 1.3
```

1.3 是预留协议开销、重传与峰值的预算系数，不是固定协议开销。如果丢包严重或链路容量随时段变化，要增加余量或降低档位。

1080p 举例：上传原画面 8 Mbps、回传 10 Mbps、直播伴侣推流 8 Mbps，本地上传的预算为 `(8+8)×1.3=20.8 Mbps`，下载预算为 `10×1.3=13 Mbps`。推荐 30 / 25 Mbps，是为了保留实际直播时的进一步余量。

服务器建议实测上下行各至少 50 Mbps 稳定可用；这个建议高于单路最低需求，目的是覆盖共享线路波动、远程维护和调试。不要把商家标注的共享峰值带宽当成独享保证。

## 2. Mbps、MB/s 和宽带套餐

- `8 Mbps ≈ 1 MB/s`，两者差 8 倍。
- “千兆宽带”通常侧重下载，上传可能远低于下载。
- 即使测速网站很快，到租用机房的链路仍可能丢包、拥堵或绕路。
- 优先使用有线网；在实际晚间直播时段测试到目标服务器的双向吞吐。

竖屏 720×1280 与横屏 1280×720 的像素量相同，1080×1920 与 1920×1080 同理。画面内容和编码实现仍会影响实际码率。

## 3. 为什么必须压缩

720p / 30 FPS，BGRA 原始帧：

```text
1280 × 720 × 4 字节 × 30 × 8 = 884,736,000 bit/s ≈ 885 Mbps
```

1080p / 30 FPS，BGRA 原始帧约 1.99 Gbps。原始帧适合在同一台电脑的内存 / GPU 中传递，不适合直接通过家庭公网长时间往返。

因此，本方案上传前编码一次，远程处理后回传前再编码一次。输入视频已有的压缩损失无法靠远程 GPU 自动消除；码率过低会影响人脸检测和换脸细节。

## 4. 流量费用

以十进制 GB 计，不含额外开销：

```text
每小时流量 GB ≈ 码率 Mbps × 0.45
```

| 场景 | 原视频送入服务器 | 服务器结果回传 | 两方向合计 |
|---|---:|---:|---:|
| 720p 示例：4 Mbps 上传、6 Mbps 回传 | 1.8 GB/h | 2.7 GB/h | 4.5 GB/h |
| 1080p 示例：8 Mbps 上传、10 Mbps 回传 | 3.6 GB/h | 4.5 GB/h | 8.1 GB/h |

如果云厂商只按出站计费，1080p 示例重点计算回传的 4.5 GB/h；直播 4 小时约 18 GB 出站，再加实际协议开销。若中继服务单独收费，还需按其实际计费方向另算，不能重复或漏算。

```text
总费用 = GPU 小时价 × 开机小时
       + 计费出站 GB × 流量单价
       + 磁盘 / Windows / 换脸软件授权等费用
       + 实际使用的网络中继费用
```

这些是计算方法，不是任何服务商的报价。

## 5. 影响体验的不只是带宽

| 指标 | 首轮筛选目标 | 解释 |
|---|---|---|
| 本地到服务器 RTT | 理想 ≤30 ms；30–50 ms 可测试；持续 >80 ms 不优先 | RTT 是一个往返，和实际总视频延迟不是同一指标 |
| 网络抖动 | 尽量 <10–15 ms | 抖动会让播放缓冲增大 |
| 丢包 | 尽量 <0.5%，持续接近 / 超过 1% 时排查 | RTP 与 ICMP 的测量可能不同，应看真实媒体统计 |
| 媒体路径 | 直连优先，识别是否中继 | Tailscale 或 WebRTC 连接成功不代表已直连 |
| 端到端画面延迟 | 720p 初期目标 P50 ≤300 ms、P95 ≤450 ms | 设计目标，需要实测，不能从 GPU 参数推导 |
| 持续返回帧率 | 单图基础链路目标 ≥25 FPS；DFM 单独实测 | 30 FPS 输出可能包含重复帧，不能混同有效处理速度 |

总视频延迟包括：

```text
采集等待 + 上传编码 + 上行网络
+ 远程解码 + 输入虚拟摄像头等待
+ 换脸处理 + 输出采集等待 + 回传编码
+ 下行网络 + 本地解码 + 输出显示等待
```

上、下行网络时间之和大致对应一次 RTT，不应机械算成“两倍 RTT”。虚拟摄像头和窗口桥接可能额外产生一帧或多帧等待；AI 负载和缓冲策略也会改变延迟。

只看 `ping=20ms` 或软件界面 `30 FPS`，都无法证明端到端画面低延迟。需要把带毫秒计时或闪光标记的原画面与回传画面同屏录制，记录多次测量的中位数与高分位；跨机器时间戳需要时钟同步，外部软件也未必保留输入时间戳。

## 6. 音画同步

首版麦克风留在本地，声音不会自动增加上述视频往返延迟。应在直播端按实测增加音频延迟；若当前直播伴侣缺少可用调节入口，评估用 OBS 合成并延迟音频。

先做拍手测试，观察拍手画面和声音的对齐，再说话测试口型。远程视频延迟不稳定时，固定音频延迟只能近似补偿，应先解决网络和视频队列波动。

## 7. 验证方法

1. 本地使用有线网，关闭无关下载 / 上传，在正常直播时段测速。
2. 租机前取得机房测试地址；短租后测本地到实际机器的 RTT 和双向可用吞吐。
3. 用 `iperf3` 分别测正向与反向，优先在受保护组网内运行；再用真实 WebRTC 统计确认。
4. 先不换脸做回环，区分网络 / 编码问题与 AI 处理问题。
5. 开直播伴侣实际推流，再测一遍，防止测试时没计算第③段上传。
6. 正式录入结果前持续至少 60 分钟，记录高峰时段、丢包、P50 / P95 延迟、有效帧率与实际码率。
