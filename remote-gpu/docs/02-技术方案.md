# 双端视频传输与换脸桥接

状态：正式架构规划与原型实现说明。默认单个用户、一路视频、两台 Windows 电脑。换脸软件安装在远程 GPU 电脑上。

0.1 原型使用 Python / Tk + aiortc / PyAV，先验证摄像头桥接和真实 WebRTC；已有打包 EXE。原型采用 H.264 软件编解码、最多 720p，并复用 FaceLive 驱动的独立通道 1（设备名 `FaceLive Camera #2`）作为远程输入，与默认通道 0 的内核对象分开。后续 GStreamer / NVENC 与 C# 整合仍是规划，尚未实现。实际操作见 [使用说明](05-双端原型使用说明.md)。

## 1. 是否需要单独的软件

需要一个双端视频传输工具：本地运行客户端，远程运行 Agent。它们负责视频采集、压缩、传输、解码和虚拟摄像头桥接，不同步视频文件，也不依赖远程桌面画面来承载正式媒体流。

首版不修改 DeepLiveCam Pro 2.7 / DeepFaceLive：通过系统摄像头设备输入，通过输出虚拟摄像头或独立预览窗口取回结果。

| 位置 | 模块 | 职责 |
|---|---|---|
| 本地 | 摄像头采集 | 选择真实摄像头、分辨率、帧率，预览并上传 |
| 本地 | WebRTC 会话 | 协商视频、连接远程、统计 RTT / 丢包 / 码率、重连 |
| 本地 | 输出桥接 | 回传视频解码后送入 `FaceLive Camera` |
| 远程 | 接收桥接 | 将收到的视频写入 `Remote GPU Input` 虚拟摄像头 |
| 远程 | 换脸软件 | 读取上述输入，执行单图或 DFM 换脸 |
| 远程 | 结果采集 | 只读取换脸结果摄像头或指定预览窗口 |
| 远程 | 结果发送 | 压缩处理结果，通过同一 WebRTC 会话的反向视频轨道回传 |

虚拟摄像头与写入者在同一台机器上工作。网络不直接“共享 USB 摄像头”，而是在远程新建一个承接视频帧的输入设备。

## 2. 摄像头和软件的连接顺序

### 本地电脑

```text
真实摄像头 → Local Client → 网络上传
网络回传 → Local Client → FaceLive Camera → 抖音直播伴侣
本地麦克风 → 可调音频延迟 → 抖音直播伴侣
```

本地真实摄像头只由客户端采集；直播伴侣选择结果虚拟摄像头，避免独占设备冲突。回传画面不再重新上传。

### 远程电脑

```text
网络上传 → Remote Agent → Remote GPU Input
Remote GPU Input → DeepLiveCam Pro 2.7
DeepLiveCam 结果摄像头 → Remote Agent → 网络回传
```

如果 Pro 2.7 没有可用输出摄像头：

```text
DeepLiveCam 独立结果窗口 → Windows Graphics Capture / OBS → Remote Agent
```

不默认录制整个远程桌面；应固定到结果窗口。预览窗口能否独立显示、能否后台采集、断开远程桌面后是否继续输出，都需要验证。

### 避免摄像头回路

远程输入和输出必须为不同设备，并记录稳定设备 ID，而不只依赖设备列表顺序。逻辑上的 `Remote GPU Input` 在 0.1 中对应 `FaceLive Camera #2`（通道 1），使用 `UnityCapture_*1` 对象，避免与软件默认通道 0 的 UnityCapture 输出串流。若第三方软件也使用通道 1，则需重新分配通道，不能假定不会冲突。

本地现有 FaceLive 程序也可能向同一个 `FaceLive Camera` 写帧。独立远程客户端运行期间只能有一个写入者；以后整合进现有主程序时，必须切换会话归属，停掉另一后端的帧写入和空闲帧发送。

pyvirtualcam 的官方说明也明确指出，OBS 内置虚拟摄像头只有一个实例，不能同时作为 Python 输出和 OBS 最终输出；若采用 OBS 备选链路，要用独立输入设备。[pyvirtualcam 说明](https://github.com/letmaik/pyvirtualcam)

## 3. 网络与媒体选型

### 正式传输：WebRTC + H.264

采用一个双向 WebRTC 会话，上传和回传各一条视频轨道。通过信令服务交换 SDP 与 ICE 候选；媒体通过 ICE 选择直连或 TURN 中继。WebRTC 实现支持不同方向独立编码，不代表两方向必须使用相同码率。

优先 H.264，首版目标 720p / 30 FPS。编码选择实际可用的本地硬件编码器；远程优先 NVIDIA NVENC，关闭 B 帧和长时间前瞻，按网络反馈调节码率并验证关键帧恢复。软件编码作为兼容退路，不能把“用了 WebRTC”当成“已经用了 GPU 编解码”。

工程候选：C# / WPF 双端壳 + GStreamer 原生媒体层。官方 `webrtcbin` 提供 SDP、ICE 和双向轨道能力；`nvh264enc` 提供 NVIDIA H.264 编码。正式采用前先做 Windows 插件打包、硬件编码与虚拟摄像头兼容性验证，固定可用版本，不承诺某个未经验证的 .NET 绑定包可直接工作。

资料：[webrtcbin](https://gstreamer.freedesktop.org/documentation/webrtc/index.html)、[nvh264enc](https://gstreamer.freedesktop.org/documentation/nvcodec/nvh264enc.html)、[Windows 安装与部署](https://gstreamer.freedesktop.org/documentation/installing/on-windows.html)。

### 首轮连接：受保护的组网 + 直连优先

原型可先把两端加入同一 Tailscale 网络，减少家庭公网地址和端口映射配置。必须检查 `tailscale ping` / 连接状态是否直连；Tailscale 也可能走中继，不能把接入成功当成低延迟直连。[连接类型说明](https://tailscale.com/docs/reference/connection-types)

最终保留公网 ICE / TURN 方案。信令走 WSS / HTTPS，媒体由 WebRTC 加密。UDP 不通时需要验证 TURN over TCP / TLS 等退路，不能认为单独映射一个 HTTP 端口就能让 WebRTC 媒体穿透。网络权限在租机前确认。

### 备用验证方式：OBS + SRT

若先用现成工具验证链路，可以评估 OBS / FFmpeg + 两路 SRT。它仍需要远程输入虚拟摄像头桥接，不是安装 OBS 就自动完成上传和回传。

SRT 便于 OBS 收发，但重传缓冲会增加两段媒体路径的延迟；OBS 文档给出的默认 latency 为 120 ms，具体还要按链路 RTT 调整，因此不把它作为最低延迟的默认终版。[OBS SRT 指南](https://obsproject.com/kb/srt-protocol-streaming-guide)

## 4. 队列、故障与音画同步

- 应用层原始帧队列只保留 1–2 帧，满时丢弃旧帧；网络解码仍按编解码依赖正常处理，不能随便丢压缩 P 帧。
- 输入序号和采集时间随可控链路记录。外部换脸软件会重打时间戳，首版不能保证输入与输出逐帧精确关联；总延迟用同屏时钟或闪光录像实测。
- 无输出 / 断流时显示状态并切换本地备用画面或黑场；不无限保留失效画面。恢复后清理旧帧并请求关键帧。
- 软件模型未检测到脸时可能回显原始画面，这属于换脸软件行为；“网络断流备用画面”不能替代软件自己的掉脸保护。
- 首版麦克风留在本地，不做远程往返；由于视频增加延迟，要提供音频延迟参数。若直播伴侣没有可靠的可调延迟，可通过 OBS 合成音视频再送平台，具体捕获与音频路由需验证。
- 输入、远程结果、网络、输出虚拟摄像头分别显示 FPS；只读软件 FPS 无法证明端到端 30 FPS。

## 5. 与现有项目的衔接

现有项目是 C# / WPF / .NET 10 Windows 程序，当前通过 Xmax SDK 处理远端媒体。新方案先做独立双端，待链路稳定后接入主界面。

| 现有文件（相对仓库根） | 现状 | 后续复用方式 |
|---|---|---|
| `app/Services/VirtualCamera.cs` | 写本地 FaceLive Camera，共享内存输出，支持裁剪 / 缩放 | 复用帧输出思路；必须检查单写入者和连接资源归属 |
| `app/Services/DirectShowCapture.cs` | FFmpeg 采集，直接依赖 `Xmax.SDK.ExternalFrameSink` | 提取通用原始帧回调后供新后端使用，不能未经修改直接移植 |
| `vcam/shared.inl` | UnityCapture 共享内存协议 | 参考创建独立远程输入摄像头，设备和内核对象需改名隔离 |
| `app/MainWindow.xaml.cs` | Xmax 会话、远程帧回调、空闲帧发送等集中在主界面 | 后续增加独立会话抽象和后端选择，不直接替换 SDK 调用 |
| `.github/workflows/build.yml` | 构建现有程序和虚拟摄像头 | 新远程端验证稳定后再增加单独构建产物 |

后续正式版建议目录（当前原型实现位于 `rgpu/`，部署脚本位于 `deploy/`，测试位于 `tests/`）：

```text
remote-gpu/
  client/       本地采集、连接、预览、虚拟摄像头输出
  agent/        远程接收、输入虚拟摄像头、结果采集
  shared/       会话协议、状态、版本与配置
  native/       媒体桥接与独立输入虚拟摄像头
  deploy/       Windows 部署、网络和环境检查脚本
  tests/        环回、队列、断线、实际设备联调
  docs/         调研、技术方案、带宽、租机和验收
```

## 6. 首版与后续功能

首版：本地选摄像头、连接服务器、预览回传、选择结果设备、输出到直播伴侣、显示码率 / RTT / FPS / 直连状态。远程先手动启动 Pro 和选择模型。

后续：在确认有公开控制接口后再实现远程切模型 / 调参；没有接口时不依赖脆弱的鼠标坐标自动化。进一步减少摄像头桥接和 CPU / GPU 拷贝，则另行评估插件或源码适配。
